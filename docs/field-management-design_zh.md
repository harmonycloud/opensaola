# OpenSaola 字段合成、写入与恢复设计提案

2026-11-18，供 dev 架构评审。建议保留包渲染契约，为持续管理的共享资源建立一个写入入口，由同一份字段计划负责修改和验收。本文保留方案评审时的设计与取舍。当次实现和验证结果见[验证记录](field-declaration-validation_zh.md)。历史基线为正式版 v1.4.0 和本地 dev HEAD 617cb7b，上一轮的 v2 修改仍在工作区。

## 二、哪些入口必须分清

| 入口 | 允许读取什么、负责什么 | 建议 |
| --- | --- | --- |
| Baseline + MID + PreAction | 按包约定合成一次最终业务声明 | 保留现行输入兼容性。MergeArray 中 name 或 serviceAccountName 可匹配对象，没有可比键可按位置合并，空数组不会清空已有数组。原生 PodSpec 的挂载按 mountPath 区分，初始化容器支持调整已声明成员的顺序。此处没有集群归属含义 |
| MID 主资源、MID/MO Configuration 的可变对象 | 从最终声明、当前实际资源、上次成功记录决定本次写入 | 共用同一规划和执行入口。服务层只提供目标身份与声明，禁止把完整 live 混入声明 |
| 暂停与恢复 | merge 比较暂停前后两份实际状态，持久化经允许的 override。apply 按既有恢复策略使用当前声明 | 先决定采纳什么，再将结果交给普通写入入口。保持已有 override 对数组整体处理的读取语义；同 generation 重试无须重放有副作用的 PreAction |
| MiddlewareAction | 一次性操作目标，动作可能有 CUE、CMD、HTTP 和显式删改 | 旧实现将完整 live 与输出合成后交 Force Apply，可能把未涉及字段带入 manager 归属。当前已有对象的编辑依据 API schema 定位成员，并以包含 UID、resourceVersion 校验的 JSON Patch 只提交发生变化的字段。动作省略字段保留。需要后续普通更新持续维持的配置应经 MID 或已有持久配置入口表达 |
| MO 自身 Deployment、RBAC、Job、status、整资源清理 | 管理专属对象、一次性任务、状态或整个对象的生命周期 | 逐调用点确认职责。MO Deployment 目前存在比较后整体覆盖 spec 的路径，若需与别人共享 spec 应迁入同一 writer。真正单方负责的对象可继续用 SSA。Job 执行、status 子资源、owner 校验及删除策略保留独立入口 |
| CLI / 包 | 产生和安装输入，展示 MID；CLI 的现有 dry-run 并非控制器最终提交结果 | 不复制字段归属算法，不增加包内删除清单。如需对用户展示最终差异，应消费控制器同一份计划的脱敏结果 |
| 主 CR 重建 | 确认目标确实缺失，按允许的方式安全渲染并 create-only | 与字段更新分开交付。只有本次成功 POST 的证据可用于识别有依据的规范化。重试 GET 已出现的对象按未知旧资源保守建档。临时读失败和“已创建、待建档”是两个状态 |

对应代码：[CUE Action](../internal/service/middlewareaction/execute_cue.go)、[Action 写入](../internal/k8s/customresource.go)、[MO Deployment](../internal/service/middlewareoperator/deployment.go)、[重建](../internal/service/middleware/rebuild.go)。

## 三、共享资源只计算一次字段计划

一次正常更新的输入是**这一轮最终渲染并经有效 override 处理的声明、上次确认声明、同一 UID 的当前资源、字段结构和可解释的外部 Apply 记录**。对象归属和暂停状态先检查。每项计划包含结构化路径、动作及成功条件。路径保留字段、关联键元组或 set 成员的边界，不能用点分字符串充当身份。展示时再脱敏。

| 当前声明 | 已知历史与现场 | 动作及成功条件 |
| --- | --- | --- |
| 明确设值，包括显式 null | 即使上次声明相同 | 落实该值，按已知类型验证其语义。值不可能合法落地时返回字段错误 |
| 省略，历史也没有 | 现场值可能由 Operator、用户或准入产生 | 保留，不把它补录成 OpenSaola 声明 |
| 省略，曾经声明，现场仍是上次可确认的值 | 无阻止删除的字段归属 | 删除或恢复可信 API 默认；无论规划时是否已缺失，都验证本次真实响应 |
| 省略，曾经声明，但现场被改写或该字段被另一 Apply 管理者保护 | 删除会覆盖对方改动 | 在提交前拒绝整个目标资源的写入，保留历史，返回具体字段。解除冲突后同一配置可重试 |
| 省略整个关联成员，里面还有独立外部字段 | 部分子字段可删 | 清除曾声明的子字段，保留外部内容及其必要关联键。外部只管理同一个成员的 env 不阻止删除自己的挂载。若对方管理的恰是待删字段，或者真正的 atomic 祖先，则阻断 |

**字段结构只有一种解释，贯穿计划、补丁和验收。** 先遵循 Kubernetes schema 的 granular map、list-map、set、atomic、复合键和键默认值。仅在 schema 确实没有描述内部结构时沿用 OpenSaola 既有的唯一非空 name 约定。显式 atomic 的具名数组仍是整体。重复或混合身份不能唯一定位时停止。历史命名数组在现场已变成对象，属于外部改写。遍历覆盖上次和本次声明的所有身份，再读取现场对应值，避免现场暂时缺失导致漏验。对 SSA 的 granular 成员存在标记、具体叶子以及 atomic 整体分别解释。

**默认值和外部注入分开。** 支持的 CRD schema 默认、对应 Kubernetes 版本可核对的原生默认化和已注册类型合法省略，统一由类型处理层解释。验收应覆盖 Deployment 从显式 replicas=3 恢复为 1、官方 CRD 的 false 合法省略、第三方 opaque 字段被重新插入。dry-run 可以证明请求能过准入，但单凭 dry-run 中出现一个值无法证明它是可信默认。对无法证明的规范化保守返回具体原因，不将 admission 新增的业务字段补进删除历史。对历史中已记录的默认值保留旧语义读取，遇到无法辨别的值不扩大删除权。

**同一份计划决定三次检查。** 本地拟写结果、server dry-run、真实提交响应，都用相同路径及成功条件核对。每个已有目标一次提交所有业务变更，带 UID、resourceVersion 前提。RV 冲突后重读重算。若实际提交才发现准入改写，真实对象可能已变更，应记录未完成并重试，不报告已回滚业务字段。两个 Kubernetes 对象之间没有这笔单对象写入的原子性。

Kafka 的具体结果可以用一条规则预测。MID 原来声明 broker 的 log 挂载和 log 卷，外部在 broker 增加 AUDIT_KEEP 和 resources。MID 同时省略 containers 和 volumes 后，留下 broker、AUDIT_KEEP、resources，卷和挂载都应消失。若外部把挂载路径从 /root/logs 改成 /root/external-drift，则报冲突，卷也留在原处。本地 Kafka 包的 [KafkaCluster CRD](../../dataservice-baseline/kafka/crds/crd-kafkacluster.yaml) 保留未知结构，没有给这个嵌套列表声明关联键。原生 Pod 模板中的 volumeMounts 使用 mountPath 作为键，同一个卷可挂在两个路径。现有包若在渲染时已经按 name 合并掉一项，writer 无法还原；应保留包级配置样例做对照测试，调整包输入合并语义须独立版本化。

## 四、历史恢复收口为一个可定位的记录

每个受管目标使用按 owner UID、逻辑来源、目标身份和 UID 可确定定位的记录。建议原型采用 owner 命名空间的一个 Secret，以自身 resourceVersion 做并发校验，保存**最近确认的声明**及**最多一笔待确认操作**。这是从“不可变记录加目标注解指针”转为可变记录的内部取舍，需单独评审。目标注解可辅助定位和识别操作；它丢失时仍能找到已有历史。继续压缩敏感内容、使用 ownerReference 和现有权限边界，按 Kubernetes 的 Secret 大小限制预检，不截断。此查找规则用于已有目标。首次 POST 前还没有目标 UID，首装只按明确声明建档；POST 响应丢失后的普通 GET 不产生新的默认值归属证据。目标重建产生新 UID，旧记录不跨 UID 授予删除权。

1. 先持久化本次尝试。保存原目标 UID/RV、操作标识、声明变化与完整验收条件，覆盖“删 A 同时加 B”。相同目标同一时刻最多一笔待确认操作。记录创建或更新失败，业务对象不写入。
2. 对目标发送一次受条件保护的写入，检查真实结果。确认成功后才以 Secret 的版本条件提升为新历史。写入超时、确认失败、进程重启时，保留旧确认声明和待确认操作。
3. 下次先读取这笔操作和现场。如果结果已满足，包含合法默认回填，先确认原操作，再处理最新 MID。这样撤回“删 A 加 B”时，可以识别 B 是上一操作声明的字段。若目标仍处于原 RV，需重试或通过目标 RV 条件使迟到请求失效，之后才能换计划。若 RV 已变化且结果部分匹配，按可证实的变化继续或报告冲突；不能用旧计划覆盖新的 MID 或外部改动。
4. 缺失旧注解时先查稳定记录；记录损坏、身份不匹配、存在多份候选或前次结果无法安全区分时明确失败。不能因为失去指针便把曾经管理过的对象当成第一次见到。新旧记录的过渡和目标删除时的回收单独实现。不得按名称或年龄推断活动记录可删。

两个对象无法共同提交。若操作回执与归属证据均已丢失，另一方还能写出同一值，就无法靠 GET 证明谁写过这个值。此时要保住现场并解释冲突。上面的状态机是拟验证的简化方向，仍需验证旧请求迟到、并发 leader 切换、对象同名重建、记录超过 Secret 限制，以及旧控制器混跑的行为，之后才能移除旧指针补偿机制。

## 五、为什么不把所有共享资源切到纯 SSA

纯 SSA 适合拓扑清楚、可以接受 Kubernetes 放弃归属语义的对象。共同管理的字段被一个 manager 省略后，其他 manager 可以继续持有该字段；API 可以成功返回。无关联标记的第三方 CR 列表默认是 atomic，Force 也不会给数组添加按 name 共享的能力。OpenSaola 目前要求共享 Kafka 的 opaque 容器列表、保护外部字段，并对未实现的明确删除报错。这三条仍成立时，纯 SSA 无法等价替代。反过来，在同一个对象上先用 SSA 写一部分、再用另一种补丁删挂载，会增加两个可分别成功的提交点。建议在对象层选择写入方式，同一共享目标只有一套行为。[Kubernetes SSA 归属与列表拓扑](https://kubernetes.io/docs/reference/using-api/server-side-apply/) · [Kubernetes 更新与并发控制](https://kubernetes.io/docs/reference/using-api/api-concepts/#updates-to-existing-resources)

## 六、替换顺序与合入条件

1. **冻结语义，先把失败固定成测试。** 将专项审查的十个反例变成可重复回归。按输入组合生成性质测试：未声明且无历史的字段保留，受保护的删除不提交，当前及历史声明的检查不因现场暂缺而消失，同一操作可重复，重试或撤回不丢待确认历史，结构化路径互不串用。保留 Kafka 原包的 CR、StatefulSet、Ready Pod 和生产消费验收。
2. **先交付一个完整的共享写入切片。** 以已经发布的 v1.4.0 为行为参考，把工作区候选作为用例来源。先用只读模式对相同输入比较新旧计划，解释差异，不做双写。第一批包含计划、验收、持久重试和旧历史读取，从 MID 主资源的 Kafka 和一类原生 Configuration 同时打通。处理默认值和外部 SSA 的规则必须在这一批验证，不能留到 Kafka 正常场景通过以后。
3. **渐进接续既有实例。** 无历史只登记当次明确声明；v1 按其原有字段边界解释，不能因为现在认识 name 就追删以前的 atomic 子项。开发/试用环境若有 v2，先解析未确认候选及旧基线。有歧义停止并给出可操作原因。相同 owner 或逻辑来源的身份验证沿用现行规则。首次安全更新成功后再切换记录，旧记录保留至确认。暂停中的实例等原流程结束；迁移依靠正常更新，无批量 CLI，无包级删除清单。新格式须有旧 writer 拒写或部署隔离，回退先验证旧读取能力，不假设换回二进制即可。
4. **有替代才删代码。** 淘汰普通 V1/V2 并行生成写入结果、验收时再做一遍合并、用不同路径编码做删除检查、同一对象补偿切换历史指针等入口。旧格式留下窄的解码/边界转换层。Action 改为增量写单独交付；MO 独有资源分别决策。主 CR 重建与暂停状态机分别验收，避免一个挂载修复同时改变生命周期。

十项反例的验收归属如下，每项都需要正向结果和失败后落库状态断言。

| 验收位置 | 必过反例 |
| --- | --- |
| 字段路径与结构 | 列表现场改对象不得误删；仅历史存在的成员被插回不能假成功；带点字面键和嵌套路径必须独立（含 v1 迁移） |
| SSA 与默认化 | 外部只管 env 不妨碍删 mount；原生 replicas 删除后接受可信 1；默认已回填而确认失败，同配置可重试 |
| 历史恢复 | 目标指针丢失且旧字段重插仍能拒绝；撤回混合增删可清除已确认新增字段，保留外部字段 |
| 重建与生命周期 | 重建读回外部字段不能收编；健康实例一次读失败不会触发非 CUE 重建并持续不可用 |

交付时按三项结构结果验收：每个共享目标只有一个持续写入入口；写入和验收使用同一份字段计划；历史未确认时，总能定位该笔尝试或明确解释为什么必须停止。代码行数和 Kafka 单个示例通过都无法替代这三项检查。
